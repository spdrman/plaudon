# O1.2 — Rust audio playback (cpal) and the Opus decode gap

**Status:** complete. **Date:** 2026-10-11. **Spec:** §5.4, §8.1, §7.9, App. A.4.
**Issue:** EPIC O #197, task O1.2 (#200). **Consumers:** O1.5 (#203, player and waveform),
O2.3 (#207, device import).
**Measured on:** macOS 27.0.0, arm64 (Apple silicon), Rust 1.99.0.

The React shell got playback free from the browser (`<audio src="plaudon-media://…">`). An egui
shell has no such thing, and `docs/EGUI_MIGRATION_PLAN.md` risk R2 names this the largest new
capability in EPIC O. This note answers two questions with measurements rather than with opinion:

1. Can a Rust process open an output device and play audio reliably enough to build a transport on?
2. What exactly is still missing for Opus, which the PLAUD device path produces?

Both prototypes were run outside the repository (scratch crate), so no dependency was added to the
workspace by this task. The crates named below are **candidates with evidence**, not decisions;
adding them is O1.5's change, with the licence-register rows that implies.

---

## 1. Output playback with `cpal` — feasible, measured

Prototype: `cpal` 0.16 (the version filmcraft uses), default host, default output device, an f32
sine callback, 500 ms of playback, counting frames and stream errors.

```
host: CoreAudio
device: Ok("JLab JBuds Lux ANC")          # a Bluetooth output, deliberately not the built-in one
default config: SupportedStreamConfig { channels: 2, sample_rate: SampleRate(44100),
                                        buffer_size: Range { min: 14, max: 1024 },
                                        sample_format: F32 }
supported:      16 kHz stereo f32; 44.1 kHz stereo f32
played 20992 frames in 547.25 ms (0.48 s of audio at 44100 Hz), stream errors: 0
```

Findings:

- **It works, first try, with no system package on macOS.** CoreAudio is reached through
  `coreaudio-rs`/`objc2-*`; on Windows it is WASAPI, on Linux ALSA (`libasound2-dev`, which
  `scripts/e2e-remote.sh` already installs for the MARS image).
- **The device dictates the format.** The default output here offers only 16 kHz and 44.1 kHz; a
  recording at 48 kHz (every device-derived Opus file) therefore needs **resampling in our code**.
  `plaudon_audio`'s canonical-PCM path already resamples, so the player must either reuse it or
  resample per block.
- **The callback is a realtime thread.** It must not allocate, lock, decode or touch SQLite. The
  shape that follows is the one filmcraft proved and that
  `docs/EGUI_REFERENCE_COMPONENTS.md` §5.1 recommends vendoring the ring buffer from: a decode
  thread fills an SPSC ring, the audio callback drains it, and underruns are counted rather than
  hidden.
- **Playback position must come from the device, not from the frame clock.** egui frames are not a
  clock (and in kittest they do not advance real time at all), so the transport state must be
  "frames consumed by the callback", published through an atomic and read by the UI.
- **Licence:** `cpal` 0.16 is Apache-2.0; its macOS tree is `objc2-*` (MIT), `coreaudio-rs` (MIT or
  Apache-2.0). All inside the current `deny.toml` allowlist. Note that `cpal` 0.18.2 is current;
  O1.5 should take the newest version that still builds on all three platforms and record the row it
  actually ships.
- **Boundary check:** `tests/integration/tests/workspace_layout.rs` forbids `objc2` *in
  `crates/domain` and `crates/app-core`*. A playback module therefore belongs in `crates/audio` or
  the binary, never in the core two.

### What O1.5 still has to build (not prototyped here)

| Capability | Why it is not free |
| --- | --- |
| Seek while playing | drain the ring, reset the decoder, re-prime; the position atomic must not jump backwards for the UI |
| Speed control (0.5×–2×) | requires resampling or a time-stretch; naive resampling changes pitch, which the React player did not do |
| Volume | per-sample gain in the mixing step, with no clipping at 1.0 |
| Device loss (Bluetooth disconnect) | `cpal` reports a stream error; the transport must pause and surface an honest state, not silently stop |
| Gapless/looping | not needed for V1 |
| A fake output for tests | kittest cannot use a real device; the player must take an `AudioOut` trait so tests inject a counting fake |

## 2. Opus — still a gap, and now measured precisely

`docs/spikes/A1.4-audio-decoder-coverage.md` found that Symphonia 0.5 with our feature set cannot
decode Opus, which matters because device `.ASR` sidecars are remuxed to Ogg Opus by
`plaud_protocol::remux_to_ogg_opus`. Two new facts:

**(a) Upgrading Symphonia does not fix it.** Symphonia 0.6.1 (released since A1.4 was written) still
publishes no `opus` feature: its feature list is `adpcm, aac, aiff, alac, ape, caf, flac, id3v1,
id3v2, isomp4, mkv, mp1, mp2, mp3, mpa, ogg, pcm, vorbis, wav` plus the SIMD options. There is no
Opus decoder to enable.

**(b) The container half already works; only the codec is missing.** Demuxing
`tests/fixtures/audio/valid/tone-mono-16k.opus` with Symphonia 0.5 (`ogg` feature, the one we
already build):

```
track 4046724258 codec CodecType(4101) opus=true rate=Some(48000) channels=Some(FRONT_LEFT)
symphonia decoder: UNAVAILABLE (unsupported feature: core (codec):unsupported codec)
demuxed 51 opus packets, 3689 bytes
```

So Plaudon can parse the Ogg stream, identify the Opus track and obtain packets today. What is
needed is a packet decoder.

### Candidates, with licences

| Crate | Version | Licence | Kind | Note |
| --- | --- | --- | --- | --- |
| `opus` | 0.4.0 | MIT or Apache-2.0 | bindings to libopus (C) | mature; adds a C build dependency and belongs behind ADR-0015's out-of-process policy |
| `audiopus` | 0.3.0-rc.0 | ISC | bindings to libopus (C) | release candidate since several years; not a basis to build on |
| `opus-decoder` | 0.1.1 | MIT or Apache-2.0 | **pure Rust**, decoder only | measured below; MSRV 1.85 (within our 1.90); one `unsafe` occurrence in the crate |
| `rusty-opus` | 1.0.1 | BSD-3-Clause | pure Rust, encoder + decoder | BSD-3 is on the `deny.toml` allowlist |
| `opus-pure` | 0.2.2 | BSD-3-Clause | pure Rust | MSRV 1.88 |
| `moosicbox_opus_native` | 0.4.0 | MPL-2.0 | pure Rust, Symphonia-shaped | MPL-2.0 is allowed; pairs with `moosicbox_opus`, a Symphonia `Decoder` implementation |

### Measurement: a pure-Rust decoder on our own fixture

Feeding the 51 demuxed packets to `opus-decoder` 0.1.1 (`OpusDecoder::new(48_000, 1)`,
`decode_float`):

```
decoded 51 packets -> 48960 samples (1.020 s at 48 kHz), peak 0.130, estimated tone 440.2 Hz
debug build:   124.8 ms   (~8× realtime)
release build:  32.7 ms   (~31× realtime)
```

The fixture is a 440 Hz sine (`scripts/make-audio-fixtures.sh` line 18), and the decoded signal
measures 440.2 Hz by zero crossings, so the decode is not merely "no error" — it reproduces the
source tone at the right frequency and a sane level.

### Recommendation for O1.5 (#203)

1. **Prefer a pure-Rust decoder**, because it preserves the property A1.4 valued most: the support
   matrix does not vary by host, and no C parser touches untrusted bytes. On today's evidence
   `opus-decoder` works on our fixture; `moosicbox_opus` is the more interesting shape because it
   plugs into Symphonia's `CodecRegistry`, which is where the rest of our decoding lives.
2. **Do not adopt one on this evidence alone.** Before it ships, require: (a) decoding a *real*
   device-derived file — `plaud_protocol::remux_to_ogg_opus` output from a captured `.ASR`, not a
   `ffmpeg`-encoded tone; (b) a differential test against libopus on a corpus; (c) the hostile-input
   contract A1.4 established (truncated, forged length, zero length) failing closed with a typed
   error and no panic; (d) a fuzz target, since this is a parser of untrusted input (`fuzz/` already
   has the harness shape).
3. **Keep libopus as the fallback**, not the default: if the differential test fails, link libopus
   behind the ADR-0015 out-of-process policy rather than shipping an approximate decoder.
4. **Until one lands, the honest behaviour is the current one**: `UNSUPPORTED_CODEC`, never an empty
   transcript and never silent playback. Playback of a device-derived Opus file must say it cannot
   be played, for the same reason.

## 3. What this means for the egui migration

- Playback is feasible and is not a reason to keep the webview. It is, however, real work: the
  transport, the ring buffer, resampling, seek and device-loss handling are all O1.5.
- Opus is a *decoder* gap, not a container gap, and it blocks playback and waveform peaks for exactly
  the files the direct-device path produces. It must be closed in O1.5 or the device path must keep
  saying so out loud.
- Neither finding changes the O1.2 architecture: both the player and the peak builder are background
  work owned by `plaudon-app`'s runtime, reported to the interface as typed events, exactly like the
  import in the spike.
