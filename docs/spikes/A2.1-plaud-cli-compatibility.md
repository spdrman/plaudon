# A2.1 — Official PLAUD Cloud CLI compatibility

**Status:** complete as a contract; one release has now been exercised,
`@plaud-ai/cli` 0.3.15 on macOS 27.0 (arm64), against a real PLAUD account.
**Date:** 2026-10-11, updated 2026-10-12. **Spec:** §2.1, §2.6, §4.2, §7.1,
§7.2, §7.6.
**Code:** `crates/source-plaud-cli/`.

## Recommendation: (a) version-locked parser for the one tested release

Spec §7.2 offers two outcomes: (a) a version-locked parser with a
compatibility warning, or (b) postpone automated enumeration while preserving
manual import. The original recommendation was (b). Since 0.3.15 was installed
and run, we take **(a) for that exact release and (b) for everything else**,
because:

- 0.3.15 offers **no JSON or other machine-readable mode** (`plaud files
  --help` and `plaud file --help` offer none), so enumeration is a scrape of a
  human-readable table and must carry the compatibility warning permanently
  for that release.
- The npm package listing declares **no licence**, so we cannot bundle,
  redistribute or pin it. The user installs it, and the version they get is
  outside our control.
- Manual import is unconditional V1 and does not depend on the CLI at all, so
  refusing every untested release costs the user nothing.

The committed compatibility table,
`crates/source-plaud-cli/cli-compatibility.yaml`, has **exactly one row**:
0.3.15, listing format `plaud_table_0_3`, numbered-page pagination,
`machine_readable: no`. Every other reported version resolves to
`VersionVerdict::NotValidated`, which maps to the stable `CLI_UNSUPPORTED`.
A version is added only together with a sanitised golden fixture captured from
that exact release and the SHA-256 of that capture. The test
`the_committed_table_declares_exactly_the_exercised_release` makes the
contents deliberate rather than accidental, and EPIC K's ADR-0050 records the
decision and the promotion procedure.

## What is implemented and tested

**Connector state machine (§7.1).** `UNCONFIGURED → CLI_DETECTED →
AUTH_REQUIRED → AUTHENTICATED → ENUMERATING → READY`, plus `ERROR`,
`EXPIRED_AUTH` and `INCOMPATIBLE_VERSION`. Transitions are total: an
inapplicable event leaves the state unchanged rather than forcing an error, and
a test proves the only path into `READY` is a successful enumeration.

**Invocation safety (§7.1, App. A.4).** The CLI is spawned with an argument
array, never a command string, which matters most on Windows where a command
string is re-parsed by `cmd.exe`. Enforced:

- the executable leaf name is a constant (`plaud`, `plaud.exe`), searched for
  in a fixed candidate list; a user-chosen location needs a recorded explicit
  approval, and `plaud.cmd`/`plaud.ps1` shims are refused because launching
  one would require a command interpreter;
- untrusted text can only occupy a value position, as
  `plaudon_security::outbound::subprocess::CliArg::Identifier`, whose
  `[A-Za-z0-9._:-]` charset rejects shell metacharacters, control characters
  and a leading `-` rather than escaping them;
- the child environment is scrubbed by the security crate, which drops proxy,
  loader (`LD_*`, `DYLD_*`) and anything token-, secret-, key- or
  password-shaped, so nothing in our environment can redirect the vendor tool
  or hand it a credential;
- the launch itself goes through the single egress gate, so Local-only Mode
  means no process is created at all (§22(15));
- stdout, stderr and wall-clock time are all capped; exceeding a cap kills the
  child and yields `MALFORMED_OUTPUT`, and a timeout yields
  `SOURCE_UNAVAILABLE`.

**Subcommand allowlist.** `CliCommand` is a closed enum: `version`, `login`,
`logout`, `files [paging]`, `audio <id>`. The version probe is the `version`
subcommand, not `--version`, which 0.3.15 rejects as an unknown option. There
is no delete, no settings write and no firmware command, and none can be
constructed. A cursor flag is only ever a constant from
`SUPPORTED_CURSOR_FLAGS`, and a numbered page uses constants from
`SUPPORTED_PAGE_FLAGS` and `SUPPORTED_PAGE_SIZE_FLAGS`, so a compatibility row
cannot introduce a new flag without a code change.

**Error mapping (§7.6).** Every parser and state failure maps to a stable code
— `CliMissing`, `CliUnsupported`, `AuthenticationRequired`, `MalformedOutput` —
and a test asserts that a vendor error string containing a session token
survives into neither the error message nor the mapped code.

## What the 0.3.15 session answered

- **Machine-readable output: no.** 0.3.15 has no JSON mode, so the listing is
  scraped under a version lock and the compatibility warning stays on.
- **`files` field inventory:** id, name, date, duration only. The name is
  truncated by the vendor at 35 characters, the date is day-precision with no
  timezone, and there is no byte length, no capture time and no transcript
  column.
- **Pagination: yes, numbered, not a cursor.** `-p <page>` is 1-based and
  `-s <page-size>` accepts 10..=100 (default 20). A page past the end prints
  zero files and exits 0, which is how enumeration terminates.
- **Exit codes:** a failure exits 1 and prints `✗ [CODE] message` on stderr.
  Observed codes: `NOT_FOUND`, `FETCH_FAILED`, `INVALID_ARGS`. Stability
  across releases remains unknown, which is what the version lock is for.

## Open questions this spike still could not answer

Each is recorded as a `known_limitations` entry on the `plaud_cloud_cli` row
of `compatibility.yaml`:

- Does a Google or Apple PLAUD login work with the CLI? We will **not** offer
  a token-paste workaround if it does not (§2.1, §7.5).
- Does the CLI expose vendor-generated transcripts through a supported path?
  `transcript` and `summary` subcommands exist, but this build fetches and
  imports no vendor artifacts and none was retrieved. We must not infer that
  it does because an unofficial API provides them.
- What does `plaud logout` do to a vendor session? Never run: it would sign
  the operator out of their own account.
- What are the rate-limit and session-expiry error codes? Never provoked.
- Do Windows and Linux hosts behave the same? Unexercised; only macOS 27.0
  was.

## Procedure for adding a version

Superseded by ADR-0050, "How to add a tested release". In outline:

1. Capture `plaud version` and `plaud files` output verbatim into
   `tests/integration/fixtures/plaud-cli/<fixture_id>/`, sanitised before it is
   committed: real layout, synthetic ids, no titles, no URLs.
2. Add a row to `crates/source-plaud-cli/cli-compatibility.yaml` carrying the
   observed format, observed pagination, the capture's SHA-256, `verified_on`
   and the host OSes it was exercised on.
3. Record the §2.6 download-URL observations in a `UrlContract` and add the
   observed host to the `DownloadPolicy` allowlist; the default allowlist is
   empty, so until then every download is refused.
4. Pass `PLAUDON_PLAUD_CLI_TESTS=1 cargo test -p plaudon-app --test
   plaud_real_cli -- --ignored` on the host being claimed.
5. Record the result in `compatibility.yaml`.

Nothing is auto-detected and nothing is inferred from a neighbouring version.
