## What was built

**A real scanner**, behind the `hardware-scan` feature and the
`plaud-ble-scan` binary, using `btleplug`. It is excluded from the default
build and from CI so neither touches a radio (§18.3A). It performs a passive
scan, applies the discovery policy and prints every advertisement it saw along
with the candidates that passed, and it writes nothing to the vendor control
characteristic — a scan cannot mutate a device even by accident. Verified to
compile and link on macOS with `cargo check -p plaudon-plaud-ble --features
hardware-scan`.

**A frame codec** with property tests over arbitrary input: `0x01` control and
`0x02` bulk frames, bounded lengths, the `0xFFFFFFFF` sentinel, invalid
offsets, duplicate and out-of-order chunks, zero-progress loops, offset
overflow and malformed auth responses.

**A compile-time acquisition allowlist.** Three read-only opcodes, closed
enum, no `Other(u16)`. A test enumerates all 65,536 `u16` values and asserts
exactly three decode. Every destructive opcode named upstream is rejected, and
more importantly cannot be constructed anywhere in the workspace.

## Adversarial cases (§18.6A "BLE authentication")

| Hostile case | Observed outcome |
|---|---|
| Fake advertiser using the name `PLAUD_NOTE` without the vendor service | `NotAVendorService`; not even a candidate |
| Fake advertiser using the name **and** the vendor service | A candidate, but `may_auto_connect()` is false: a name is never an identity |
| Two devices reporting the same name | Distinguished by host peripheral identifier |
| Malformed handshake / unvalidated firmware | `UnsupportedProfile`, and no later event can move it |
| Encrypted-mode offer | `UnsupportedAuth`, with no path back to the legacy handshake |
| Forged frame length | Refused before allocation |
| Missing final frame | Never `Complete`; `finish()` yields nothing |

## Honest limits

- `plaude-cli` is Linux/BlueZ-first. Its working result is **not** evidence
  for macOS or Windows (§2.5A).
- The BLE listing is a **delta of unsynchronized files**. A device that has
  synced to a phone may list nothing, and the interface must explain that
  rather than presenting an empty list as "no recordings".
- The transfer yields a compressed `.ASR` Opus sidecar, **not** the original
  stereo WAV, and we store it with `quality_class =
  compressed_device_transfer`. See A1.4: we currently cannot decode Opus at
  all, so this path needs a decoder before it is useful.
- macOS requires a Bluetooth usage description in the app bundle, or the
  operating system denies the radio. The scanner reports that denial as
  `RADIO_PERMISSION_DENIED` rather than as an empty scan.

## To produce a Supported cell

1. Run `cargo run -p plaudon-plaud-ble --features hardware-scan --bin
   plaud-ble-scan -- 8` on a real host and archive the output.
2. Record device model, observed firmware fingerprint, host OS and build,
   transport, auth route, audio format, byte count, terminal-marker
   observation and digest.
3. Commit a redacted frame trace under `tests/fixtures/ble/<device>-<firmware>/`
   with **no token bytes and no audio**.
4. Repeat the whole setup on a clean machine (§7.9 hardware shipping gate).
5. Only then add the row with `evidence_level:
   observed_on_identified_hardware` and a resolving `test_run_id`.
